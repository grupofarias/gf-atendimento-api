## Diretrizes de Desenvolvimento

### Idioma e Comunicação
- Responda sempre em português (pt-BR).
- Se não tiver certeza de algo (nome de tabela, endpoint, campo, etc.), deixe explícito e peça contexto em vez de inventar.

### TDD First
- Escreva testes antes da implementação. Testes guiam o design do código.
- Novos comportamentos devem ter cobertura de testes antes de serem considerados prontos.

### Clean Code
- Priorize clareza, legibilidade e baixo acoplamento.
- Arquivos com mais de ~200–300 linhas devem ser avaliados para quebra em módulos menores.
- Funções longas ou confusas devem ser extraídas em funções nomeadas.
- Reutilize funções existentes — evite duplicação de lógica.

### SOLID
- Aplique princípios SOLID sem exageros. Foco em responsabilidade única e inversão de dependência.
- Não crie abstrações prematuras — só abstraia quando houver necessidade real.

### Tecnologias e Padrões
- Não introduza tecnologia ou padrão novo sem verificar se é possível reutilizar o que o projeto já usa.
- Se migrar para algo novo, remova a lógica antiga por completo. Nada de código morto.

### Organização
- Scripts de execução única ficam em locais claramente marcados como temporários ou de migração, nunca no core da aplicação.
- Avanços importantes devem ser registrados na pasta `step-by-step/` (o que foi feito, por que, impacto esperado).

### PRDs e Documentação de Produto
- Se houver arquivos `.md` de produto/negócio (escopo, PRD), leia-os antes de implementar — são fonte de verdade para regras de negócio.
- Não altere PRDs sem pedido explícito.
- Se identificar inconsistências entre código e PRD, sinalize com clareza.
